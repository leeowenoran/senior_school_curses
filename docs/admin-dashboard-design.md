# 全站用户数据看板（管理后台）· 设计方案

> 目标：新增一个页面，管理员可查看**全站所有用户**的账号信息与学习数据。
> 本文基于对现有代码与云端数据库的实测结论撰写，非空想设计。

---

## 一、现状盘点（实测）

### 1.1 云端数据库真实结构

CloudBase 环境 `shanghai-env1-d3gq2odzh654c9264`，实际只有 **2 个集合**
（注意：`backend/cloudbase/schema.md` 里那份 4 集合设计**从未落地**，属历史遗留文档，勿参照）：

```
users_auth   _id = 手机号
  { phone, salt, pwHash, createdAt }

users_data   _id = 手机号
  { phone,
    data: {
      gz_progress,    // { "sid/vid/idx": { ts: 毫秒时间戳 } }
      gz_wrongbook,   // [ { key, qi, question, answer, myAnswer, subjectName, lessonName, type } ]
      gz_checkin,     // { lastDate, streak, total, history: ["2026-08-03", ...] }
      gz_recent,      // [ { sid, vid, idx, name } ]
      gz_quiz_log,    // [ { ts, key, qi, right } ]  最多保留 2000 条
      gz_favs, gz_medals, gz_comments, gz_done_count,
      phone, nickname, avatar, createdAt   // 用户信息也在 data 里
    },
    updatedAt }
```

**当前规模：`users_auth` 2 条，`users_data` 2 条。**
其中一个用户已学 4 课时 / 4 错题 / 14 条做题记录，另一个为空号。

### 1.2 两个关键结论

**结论 A：做看板所需的数据已经全在 `users_data` 里，一个文档一个用户。**
`app.js:1252` 的 `cbSyncNow()` 在同步时把 `phone / nickname / avatar / createdAt` 一并写进了
`data` blob，所以**不需要联表**，读 `users_data` 单集合即可拿到"用户信息 + 全部学习数据"。

**结论 B：趋势类指标不需要新增埋点。**
`gz_progress[key].ts` 与 `gz_quiz_log[].ts` **都带毫秒时间戳**，
`gz_checkin.history` 还存了日期数组。因此「近 7/30 天活跃、每日课时数、每日做题数、
最后活跃时间」都能从现有快照直接反推，无需改造前端埋点。
这一点显著降低了中等方案的成本。

### 1.3 现有能力缺口

| 缺口 | 说明 |
|---|---|
| **无管理员概念** | 全项目 grep 无 `admin` / `role` 相关逻辑，需从零引入 |
| **接口按用户隔离** | `gzApi` 5 个 action（register/login/changePassword/getData/saveData）全部以 token 解出的手机号为边界，**没有任何跨用户读取能力** |
| **无历史快照** | `users_data` 只存当前状态，`saveData` 是覆盖写。跨度超过 `gz_quiz_log` 2000 条上限的久远历史会丢失 |

### 1.4 顺带发现的安全问题（建议一并处理）

1. `cloud_functions/gzApi/index.js:22` 的 `SECRET` 硬编码在源码里，且已提交进 Git。
2. token = `base64(手机号).HMAC`，**永不过期**，无法吊销。
3. `Access-Control-Allow-Origin: '*'` 对所有 action 放开。

普通用户接口风险尚可控，但**管理员接口能读取全站数据，必须收紧**，否则一旦 token 泄漏即全站数据泄漏。

## 二、通用设计决策（三个方案共用）

### 2.1 管理员鉴权：云函数硬编码白名单（✅ 已实现）

> 2026-08-04 已落地。管理员账号定为 **`king`**（非手机号），定位为**纯管理员**，不参与学习、不计入全站统计。

```js
// cloud_functions/gzApi/index.js
const ADMIN_IDS = ['king'];
function isAdminId(s) { return ADMIN_IDS.indexOf(s) >= 0; }
function isLoginId(s) { return isPhone(s) || isAdminId(s); }   // 登录放开
function requireAdmin(token) {
  const id = verifyToken(token);
  if (!id || !isAdminId(id)) return null;
  return id;
}
```

理由：当前仅 2 个用户、单一管理员，白名单是**成本最低且最不易出错**的做法。
不引入 `role` 字段可避免"数据库被改写即提权"的风险（白名单只存在于云函数代码里）。
后续若需多管理员，往 `ADMIN_IDS` 里加一项并重新部署即可。

**如何在不削弱注册安全的前提下创建非手机号账号**（关键设计）：

| 接口 | 校验 | 结果 |
|---|---|---|
| `register` | 保持 `isPhone()` 不变，并对 `ADMIN_IDS` 显式拒绝 | 外部**永远无法**注册 `king` 或任何英文账号名 |
| `login` | 放宽为 `isPhone() \|\| isAdminId()` | `king` 可登录；`kingx` 等非白名单仍被拒 |
| `seedAdmin` | **`isHttp` 时直接返回「未知操作」** | HTTP 永远调不到，且不暴露该接口存在；仅 CLI/控制台可用 |

即：**只放开登录、不放开注册**，公开注册的安全边界丝毫未动。

```bash
# 创建 / 重置管理员账号（唯一入口）。注意：本仓库公开，请勿把真实密码写进文档
tcb fn invoke gzApi --params '{"action":"seedAdmin","payload":{"id":"king","password":"<密码>"}}' \
  -e shanghai-env1-d3gq2odzh654c9264
```

由运维直接建档，故不受公开注册「密码至少 6 位」限制（`login` 本就不校验密码长度）。

**⚠️ 密码强度的已知取舍**：当前采用的是一个**极短的弱密码**（应需求保留，具体值不落文档）。
登录接口 CORS 全开且无频率限制，理论上可被暴力破解。
采纳的补偿措施是「**管理接口一律脱敏输出**」（见 2.2）——即便账号失守，泄漏的也只是脱敏手机号 + 学习进度，
不含完整手机号与原始答题内容。**若日后用户量增长，务必先用上面的命令改密码。**

**落库形态**（已验证）：`users_auth/king` 与 `users_data/king` 均带 `isAdmin: true` 标记，
`users_data.king.data` 为空对象。聚合统计时用 `$match: { isAdmin: { $ne: true } }` 一行即可排除管理员，
避免"人均学习课时"被一个空号拉低。

### 2.2 服务端聚合，而非下发原始数据（推荐）

管理接口**只返回聚合后的摘要**，不下发 `gz_wrongbook` 全文、不下发完整手机号。

- 隐私：手机号一律脱敏为 `137****4089`，明文只在云函数内部使用
- 流量：单用户 blob 可达数百 KB，10 个用户就是几 MB；聚合后每人仅约 200 字节
- 安全：即便管理页被他人打开，也拿不到原始答题内容

### 2.3 页面载体：独立 `admin.html`（推荐）

不并入主站 `#/admin` 路由，理由：

- 主站 `index.html` 是给学生用的，加管理代码会增大首屏包并暴露管理入口
- 独立页面可单独设访问口令，且不受主站懒加载改造影响
- 复用 `css/style.css` 即可保持视觉一致，成本很低

## 三、三个方案

### 方案 A · 轻量只读看板

**一句话**：一个页面看完所有用户的核心指标，够用就好。

**后端**：新增 1 个 action `adminOverview`
返回：全站汇总 + 用户列表（每人一行摘要）

**前端**：新增 `admin.html` 单页
- 顶部 4 张指标卡：注册用户数 / 7 日活跃 / 累计学完课时 / 错题总量
- 用户明细表：脱敏手机号、昵称、注册时间、最后活跃、已学课时、错题数、做题正确率
- 学科热度排行：按全站已学完课时数排序的 11 个学科条形图
- 表头可点击排序

**改动面**：`cloud_functions/gzApi/index.js`（+1 action）、`admin.html`（新增）、`css/style.css`（追加样式）

**优点**：改动最小、无前端埋点、当天可上线、风险最低
**缺点**：只能看总览，无法下钻到"某个学生具体卡在哪一课"

---

### 方案 B · 完整运营后台（推荐）

**一句话**：总览 + 单用户下钻 + 趋势曲线，能真正回答"谁在学、学得怎么样"。

**后端**：新增 2 个 action
- `adminOverview` —— 同方案 A，另附近 30 天每日活跃/课时/做题数组
- `adminUserDetail` —— 传入手机号，返回该用户的 11 科进度明细、7 日学习曲线、错题清单、签到连续天数

**前端**：`admin.html`，三个页签
1. **总览**：方案 A 全部内容 + 近 30 天趋势折线（新增用户 / 日活 / 每日课时）
2. **用户**：可搜索、可排序的用户表；**点击任意行右侧滑出详情抽屉**
   - 该用户 11 科进度环形图 + 每科已学/总课时
   - 近 7 天学习节奏柱状图
   - 错题清单（按学科分组，显示题目与错误答案）
   - 徽章、连续签到、收藏数
3. **内容**：反向视角——哪些课时被学得最多、哪些题目错得最多（用于优化教材）

其他：全表导出 CSV、时间范围切换（7/30 天/全部）

**改动面**：`cloud_functions/gzApi/index.js`（+2 action）、`admin.html`、`js/admin.js`（新增）、`css/admin.css`（新增）

**优点**：
- 「哪些题目错得最多」能直接反哺内容质量，这是这个项目独有的价值点
- 趋势与下钻**全部复用现有时间戳，零埋点改造**
- 结构清晰，后续加功能有地方放

**缺点**：工作量约为方案 A 的 2.5 倍

---

### 方案 C · 数据平台化（埋点 + 事件流）

**一句话**：补齐真正的行为日志，支持留存、漏斗、时段分布。

**后端**：
- 新增 `events` 集合做行为埋点：`{ phone, type, sid, vid, idx, ts, meta }`
  （type: view_lesson / submit_quiz / login / checkin ...）
- 新增 `adminEvents`、`adminFunnel`、`adminRetention` 三个 action
- 新增定时触发云函数，每日凌晨预聚合写入 `stats_daily`，避免实时扫全表

**前端**：方案 B 全部内容 + 留存曲线（次日/7日/30日）、学习时段热力图、
学科掌握度热力图（学科 × 难度 × 正确率）、用户分层（活跃/沉睡/流失）

**改动面**：上述全部 + `js/app.js` 埋点注入 + 数据库索引 + 定时器配置

**优点**：能回答"用户为什么流失""哪个环节劝退"，指标口径规范
**缺点**：
- 工作量最大，约为方案 B 的 2~3 倍
- **当前只有 2 个用户，留存率、漏斗这类指标在小样本下没有统计意义**
- 埋点会增加每次操作的云函数调用，需关注 CloudBase 免费额度

## 五、推荐

**选方案 B。**

理由：

1. **方案 C 现在是过度设计**。2 个用户算留存率没有统计意义，而埋点一旦铺开，
   后续改数据结构的成本会陡增。等用户上到几十个再上 C 不迟，届时 B 的代码可平滑扩展。
2. **方案 A 会很快不够用**。你做这个系统是为了掌握学习情况，
   只看"总共学了 4 课时"没有决策价值，你真正需要的是"某个学生化学卡在哪一课、哪道题反复错"——这是 B 的下钻能力。
3. **方案 B 的增量成本被现有数据结构显著摊薄**。因为时间戳已存在、用户信息已在同一文档，
   B 相对 A 多出来的主要是前端展示工作，后端几乎没有额外复杂度。

**建议的实施顺序**（可分两次交付，每次都是可用状态）：

1. 第一步：云函数加 `requireAdmin` + `adminOverview`，前端出总览页 → 立刻可用
2. 第二步：加 `adminUserDetail` + 详情抽屉 + 趋势图 + 内容分析页

**同时建议处理的安全项**（约占总工作量 5%，强烈建议随第一步一起做）：

- `SECRET` 从代码移到云函数环境变量，并轮换一次（旧 token 全部失效）
- token 加签发时间与有效期（如 30 天）
- 管理类 action 的 CORS 收紧到你的正式域名
